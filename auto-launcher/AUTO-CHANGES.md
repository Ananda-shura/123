# Подбор по результатам целевых проверок

В диагностике пользователя: DoH и обычный DNS вернули один набор YouTube IPv4;
Google, Steam и ytimg дали HTTP 200, а главный YouTube — curl28 в фазе подключения/TLS.
По нулевым time_connect/time_appconnect нельзя отличить отказ TCP от остановки TLS.
Работающая HappService не доказывает VPN-подключение; пользователь сообщил, что VPN отключён.

Новый START сначала проверяет TCP, затем HTTPS без Zapret. Если TCP к YouTube проходит,
а HTTPS нет, он сравнивает четыре штатных Google TCP-стратегии: BASE, FAKE TLS AUTO ALT,
ALT8, ALT7. Все получают один и тот же выбранный доступный IP через curl-only --resolve,
затем обычный DNS. Профили меняют только TCP-правило YouTube, QUIC остаётся fake6.
Ни Game Filter, ни IPSet, ни обработка Steam/игровых диапазонов не добавлены.
Методы с timestamp-fooling не используются, глобальные TCP timestamps не меняются.

Это целевой тест гипотез, а не утверждение, что другая стратегия обязательно исправит доступ.
При отсутствии пригодного варианта никакой победитель не назначается. Результат сохраняется.
HTTP200 страницы не подтверждает HTTP3, браузерный DoH/ECH и воспроизведение видеосегментов.

Новый C#-помощник использует Windows Job Object только для процессов, созданных этим запуском.
Если назначение Job не удаётся, текущий новый процесс завершается, подбор прерывается.
В первые мгновения между созданием процесса и назначением Job остаётся небольшое окно;
не заявляется абсолютная защита при сбое ОС в этот момент.

Все исходные бинарники и драйверы сохранены, новые исполняемые бинарники не поставляются.
C#-исходник локально компилируется Add-Type после проверки SHA-256.
